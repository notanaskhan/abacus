## 1. Goal and user-visible outcome

**Goal.** Close the firm's conversation loop with its clients on Accrued, without letting a model or an agent speak for the firm:

1. **The firm's own `docs@` mailbox flows into Accrued and replies leave from it.** Microsoft Graph ingest feeds N-01's channel-agnostic Inbox, and a person replies in-thread from the firm's address with sensitive-data checks, cited outstanding items and secure upload links instead of attachments.
2. **Secure client messages.** Portal threads replace email for anything sensitive: the client writes in POR-07, the firm answers in INB-04, and every thread is tied to a client and work item, with an origin (portal message, request comment, issue question), an assignee and a "needs a reply" dot that clears only when someone replies or resolves.
3. **One place to chase clients.** BND-04 lists every request across every engagement the viewer may see, with honest counts, and bulk follow-ups that the Request Chaser drafts and a person sends.
4. **The client manages its own people.** POR-12 lets an owner invite colleagues, ask the firm to let an outside organization into one request, invite a delegate whose access waits for a §7216 consent, and see and end sessions, all inside the firm's MFA policy.
5. **Model-drafted client text exists only under ADR P-25,** off by default, per firm, after the drafter's evals pass on Bedrock. Until then every draft a real firm sees is composed by code from facts.

Invariants used below (chapter 01 §1.2): **INV-1** the agent never decides, approves, sends or resolves; **INV-2** citations are verified by code before display; **INV-3** walls hold, with no hidden counts; **INV-4** portal scopes are isolated and firm-only fields never reach a client; **INV-5** attribution is correct ("‹person› via Agent" for agent work; the client sees only the human sender).

### 3.1 Connect the firm mailbox and ingest mail (W6 ingest)

*As Felix Andersen (IT/Security), I want to connect Brightwater Hale's `docs@` mailbox once, so that client email lands in Accrued's Inbox and replies leave from our own address.*

**Context and output.** Context is built by code from registered sources (requests: open items, due, overdue; signatures: envelope state, signer progress and the KBA outcome ("Needs a handwritten signature" after three failed checks; never an unlock time, DF-11); notices: respond-by, status; review: issue questions; closes: transaction questions; tax: extension, K-1 waits) plus the firm's sign-off name and the contact's first name. The thread's last client message is included only inside the untrusted wrapper (ADR-052). Output is a closed AgentBlocks schema (ADR P-24): paragraphs and list items made of text segments, `{fact: key}` references, `{cite: fact_key}` markers and `{link: kind}` placeholders. Numbers and dates appear only as fact references; any digit run in model text that is not a fact fails number provenance and the draft falls back to the template. No markup, no URLs, no exclamation marks, no internal terms ("materiality", "Draft K-1 · pre-release", "agent", confidence, reason codes).

**Gates and stages.** The gateway enforces the ADR-115 boundary and `consent_7216` on every call, on every route and tenant, before the synthetic pass (T-01). Stage `shadow`: model drafts are stored as run records for comparison, never shown. Stage `live` plus the six P-25 conditions: model drafts shown, edited and sent by a named person. The client never sees that a draft came from the agent (chapter 05 §5.4.3 point 7: disclosure is at engagement level).

### 7.2 Obligations

- **§7216 (IRC; Treas. Reg. §301.7216):** email and portal messages about tax clients are tax return information. Bodies and drafts carry the `tri` class when the client has tax work; drafter context with TRI passes the C19 gate or falls back to the template; offshore users cannot read TRI thread bodies without an offshore consent (P-12). A delegate is a third-party disclosure: the delegate grant activates only after the taxpayer signs a disclosure consent whose text counsel approves and which is stored as a database template (F-09/T-01).
- **GLBA Safeguards Rule (16 CFR 314.4(c)(5)):** MFA for owners, signers, approvers and TRI scopes cannot be disabled by the client (POR-12 shows "Required by Brightwater Hale"); sessions are visible and endable; removal ends sessions (ADR-030's promise kept, P-54).
- **IRS Pub 4557 / WISP:** tax documents never travel as email attachments; secure one-time links instead; mechanical checks block SSNs, routing, account and card numbers in outbound text (the POR-20 rule extended to every message).
- **Professional liability (ADR P-25, RK-46):** model text reaches a client only under the six conditions; the edit diff and the sender are retained; disclosure is at engagement level in the letter's AI-use clause.
- **Confidentiality (AICPA ET 1.700):** the scope checker blocks other clients' names, accounts and out-of-scope amounts; walls apply to every read.
- **Records retention (P-14):** "Email & portal messages" 7 years; raw MIME and attachments write-once (GOVERNANCE, P-43); holds honoured; destruction only by dual-approved batch.
- **W6 write controls (P-17, RK-33):** human approval, idempotency, evidence, kill switch; delta pen test before any real firm.
- **Microsoft platform terms and publisher verification;** least privilege (one mailbox); admin consent by the firm's own Microsoft admin; Accrued processes the firm's mail as its processor under the DPA (no new sub-processor).
- **CAN-SPAM:** all emails transactional; the optional "New message from your team" email can be turned off by the client.
- **SOC 2:** change management under the freeze; access reviews include the client-service desk's firm-wide thread access.
- **Accessibility:** POR-07 and POR-12 in the portal ACR (WCAG 2.1 AA).
