# K-02 · Firm standards, rules tables & content import

> Epic specification and task backlog. Chapter 01 is the plan of record for dates, owners and scope. Decision and ADR IDs are chapter 09's (DEC-nn, ADR P-nn); repo ADR numbers are the reservations in F-02's schedule. **AY** = ayushkbhatia, **N** = notanaskhan. The CSV twin of §9 is `sections/epics/K-02.tasks.csv`.
>
> **Short version.** K-02 gives Accrued two kinds of versioned, effective-dated rules. Both live in the database and are changed by import, never by a commit.
> 1. **Platform reference sets** (contract **C21**, ADR P-62). These are global tables of public law: TY due-date rules, federal and DC legal holidays, disaster postponements, the Form 8879 form set with the Pub 1345 amount tolerances, information-return (1099) thresholds and retention minimums. The founders publish them under a two-person rule with an operator CLI until PLT-01 lands in **G-04**. A `practice` calendar engine computes due dates and clocks from them. **T-01** and **T-02** need this in production before the Sep 1, 2027 window.
> 2. **Firm standards and threshold policies** (screen **KNW-04**). These are per-tenant, versioned numbers and checklists that sort agent output and govern review: AJE thresholds, variance thresholds, materiality ranges, document confidence, review checklists, review levels, return approval (BH-TAX-02) and the SSARS 27 switch. A named partner owns each one and is the only person who can publish it. Every version carries an effective date. Content comes in through admin import, and consumers call deterministic APIs.
>
> **Nothing in K-02 calls a model.** The Accrued Agent never drafts, imports or publishes a standard or a rules table (INV-1). K-02 only provides the numbers that code uses to sort agent output.

## 3. Features and user stories

### F1 · Platform reference sets (C21 part A)

**US-1.1** As a founder acting as operator, I draft a rules table from a workbook and publish it only with the other founder's approval, so that no single person changes law-derived data and nothing is deployed.
- *Given* ayushkbhatia ran `make refdata-draft KIND=due_date_rules FILE=…` for "TY2026 federal due dates", *when* ayushkbhatia runs `make refdata-publish`, *then* it refuses with `approver_is_drafter`. *When* notanaskhan approves with a reason, *then* the version is `published`, a `reference_set_publications` row records both handles, and no migration or deploy runs (P-62).
- *Given* the workbook contains a formula, a macro or an external link, *when* it is drafted, *then* only cached values are read and problems are reported as sheet, row, column and a fixed code, never cell contents (ADR-052; `engagements/workbook.py` pattern).
- *Given* a hosted deploy is using the staging database, *when* the CLI runs against staging, *then* it refuses (`deploy_in_flight`, F-01 guard).

**US-1.2** As a consumer module, I resolve the rules in effect on a date.
- *Given* "TY2026 8879 form set" v1 effective 2027-01-01 and a correction v2 with the same effective date, *when* `form_8879_for("1065", 2026, "US", as_of=2027-07-01)` runs, *then* it returns 8879-PE from v2, with v2's id in the result.
- *Given* the app role, *when* it selects from `reference_set_versions` directly, *then* permission is denied. *When* it calls `reference_set_resolve`, *then* it sees only published versions (T03, T09).

**US-1.3** As a firm admin, I learn when a rules table changes.
- *Given* a publish, *then* each active tenant gets exactly one `reference_set.published` audit event, with system actor `operator:<drafter>` and the approver in its facts, and one "Rules table updated" notification to `firm_admin` and tax partners. ADM-07 renders the actor through `formatActor` (INV-5, T12).

**US-1.4** As K-01's KNW-02d standards mapping, I offer only standards sets that were published as reference data, so pilot firms map EBP v3 to real rows and no set arrives in a commit.
- *Given* notanaskhan approves ayushkbhatia's `make refdata-draft KIND=standards_sets` version with GAAS nonissuer · AU-C 703, SSARS and SQMS 1, *when* it publishes, *then* `standards_sets_apply` adds the three codes to K-01's `standards_sets` table, `reference_set_publications` records both handles, and KNW-02d lists exactly those sets (K-01 AC6.2; T03, T05, T20).
- *Given* a draft that adds a PCAOB or issuer set, or that drops or re-families an existing code, *then* the validator refuses it before publish (X-07, DEC-19), and no row of `standards_sets` is ever deleted.

### F2 · Due dates and clocks (C21 part A, `practice`)

**US-2.1** As the tax pilot (T-02), I get the original and extended due dates of a return from the published rules.
- *Given* TY2025 rules, *then* Ridgeline's 1065 (calendar year) is due Mon Mar 16, 2026, because Mar 15 is a Sunday (IRC §7503), and extended to Tue Sep 15, 2026. The Feld 1040 is extended to Thu Oct 15, 2026. Lakeshore's 990 (FYE Jun 30, 2026) is due Mon Nov 16, 2026, and its 8868 extension runs to Mon May 17, 2027.
- *Given* TY2026 rules, *then* the 1065 and 1120-S extended dates are Wed Sep 15, 2027, the 1041 is Thu Sep 30, 2027, and the 1040 is Fri Oct 15, 2027. A calendar-year 2026 Form 5500 is due Mon Aug 2, 2027 (Jul 31 is a Saturday), and 5558 extends it to Fri Oct 15, 2027.
- *Given* a disaster postponement for (state, county) with a window and a postponed-to date, *when* the caller passes a covered location, *then* the postponed date is returned with the notice id. Otherwise the date is unchanged.
- *Given* identical inputs, *then* `inputs_hash` and the output are identical, and both carry the reference-set version ids used.

**US-2.2** As a consumer of clocks (A-07, Q-02, T-01, N-04), I get calendar-day clocks that never roll: Oct 9, 2026 + 60 = Dec 8, 2026 (AU-C 230); Sep 10 + 30 = Oct 10 (FTC); 8879 retention ends 3 years after the later of the due date and the IRS received date. These are the I-CLOCKS golden cases (chapter 10 §10.9.3), transcribed by N (T15).
