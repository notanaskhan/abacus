# P-01 · Firm shell, sign-in & notifications

> Epic specification and task backlog. Chapter 01 is the plan of record for dates, owners and scope. Decision and ADR IDs are chapter 09's (DEC-nn, ADR P-nn). **AY** = ayushkbhatia, **N** = notanaskhan. The CSV twin of §9 is `sections/epics/P-01.tasks.csv`.
>
> **Short version.** P-01 turns the firm app's chrome into the Accrued chrome and makes it real. It covers four screens:
> 1. **SHL-01**, the toolbar: the 13 nav items rendered from F-02's `nav.ts`, with live routing, the bell dot, and measured overflow.
> 2. **SHL-03**, the firm menu: firms, the person card, the default office filter, admin links gated by capabilities, firm switching and sign-out.
> 3. **SHL-04**, notifications v2: a catalogue of kinds with read-time facts, tabs, one inline document approval with a 10-second Undo, per-kind preferences, and email through SES.
> 4. **SHL-06**, staff sign-in on **hosted WorkOS AuthKit**, behind a BFF session with an httpOnly refresh cookie. Only frame g ("Signing in…") is built inside the product. The custom in-product T15 card (SHL-06 a–f) is a sized follow-on of about 2 tasks on P-08's BFF. It needs only ADR P-54, which amends ADR-030, and is proposed for G-02 (S9–S14); until G-02 or chapter 01 §1.7.2 records it, it is deferred (§2.2).
>
> P-01 co-provides contract **C16** (notification kinds and transactional email templates in the database) with **R-01**. The contract freezes in S5.

## 3. Features & user stories

Personas and data are from the Brightwater Hale seed (F-04) at E0. Every acceptance criterion also holds under the five invariants of §3.6.

### 3.1 Toolbar and navigation (SHL-01)

**Story 1.1.** *As anyone at Brightwater Hale, I want the same calm toolbar on every firm screen, so I never lose my place.*

- **AC 1.1.1 (SHL-01a/b).** *Given* any firm user and any firm route, *when* the page renders, *then* the toolbar shows Go…, the firm pill "Brightwater Hale ⌄", the 13 items from `nav.ts` in order (Home · Engagements · Tax Returns · Files · Knowledge · Workbench · Inbox · Clients · Binders · Notices · Audits · Closes · Signatures), Support and the bell. There is no 14th item, no icon and no count on any nav item (D4; the F-02 nav test). The item that owns the route has `aria-current="page"`, the #F2F1EF background and weight 500.
- **AC 1.1.2 (SHL-01g).** *Given* a screen from the R2 list (for example ENG-10 Board or BND-04 Request tracker), *when* it is open, *then* the existing nav item that owns it is active (Engagements, Binders), taken from the manifest entry's `navArea`. Nothing is added to the bar.
- **AC 1.1.3 (SHL-01f).** *Given* any `/settings/*` route, *then* no nav item is active and the firm pill shows its pressed state (#E8E6E0).
- **AC 1.1.4 (SHL-01e).** *Given* a viewport width, *when* the toolbar measures its clusters (F-05-T18's ResizeObserver), *then* items collapse into More ⌄ in DF-39 order: Signatures first (≤ 1440), then Closes and Audits (< 1280). The nav never wraps and type never shrinks. At 1400 the full "Brightwater Hale" pill and More ⌄ are both shown, as on SHL-01a. Below 1280 the page scrolls horizontally (FE-19).
- **AC 1.1.5 (unbuilt areas).** *Given* a nav item whose landing screen is still `planned` in the manifest (for example Tax Returns before T-02), *when* a user clicks it, *then* the area renders F-05's designed flag-off or "not available yet" state (F-05-T19). It never shows a 404, a blank page or a hidden item.
- **AC 1.1.6 (SHL-01a, d).** *Given* `unread_count > 0` in the 30-day window, *then* the bell shows the dot. *Given* 0, *then* there is no dot (SHL-01d). The bell's accessible name is "Notifications, unread" or "Notifications", never a number. The unread count is polled every 60 s and on window focus (DEC-23).
- **AC 1.1.7 (SHL-01c, keyboard).** *Given* focus is not in a text field, *when* the user presses ⌘K / Ctrl+K, *then* Go… opens. G H, G T, G A, G C and G W navigate to their areas, and `?` opens the shortcuts dialog. *Given* focus in an input, textarea or contenteditable, *then* no chord fires. Hover, focus-visible and pressed match SHL-01c (interaction test).
- **AC 1.1.8 (interim Go… and Support).** *Given* P-02 has not shipped, *when* Go… opens, *then* the interim O5 frame lists the 13 areas and the shortcuts, with no search request sent. The tooltip's R2 second line ("Also: New to-do… · Load saved prompt… · Open board") is absent until the `palette` flag exists. *Given* G-04 has not shipped, *when* Support is clicked, *then* the interim O2 frame shows the support contact and the System status link.

### 3.5 Hosted sign-in and the staff session (SHL-06)

**Story 5.1.** *As any firm user, I want to sign in with my firm's policy enforced and come back to where I was.*

- **AC 5.1.1 (hosted a–f).** *Given* the staging WorkOS environment, *then* AuthKit offers Microsoft, Google and email code (Magic Auth), with **no password method** (DEC-22, DF-24), monochrome provider buttons and the Accrued wordmark (DF-41). It requires a second factor (TOTP; passkeys if AuthKit supports them [verify]) for non-SSO users. It routes `@brightwaterhale.com` users to Microsoft SSO when the organisation's domain policy enforces it (SHL-06d). Lockout follows DEC-35 values wherever AuthKit allows them to be configured [verify]. A staging smoke test asserts that no password input is present on the hosted page.
- **AC 5.1.2 (callback and session).** *Given* a successful AuthKit return to `GET /v1/auth/callback`, *then* the BFF:
  - validates `state`;
  - exchanges the code with WorkOS server-side;
  - verifies the access token (JwtVerifier: RS256, verified email);
  - **refuses** a non-SSO session without a verified second factor (`auth.sign_in_refused`; FTC Safeguards 314.4(c)(5));
  - maps the WorkOS user to an existing Accrued user, refusing unknown users with the T15 error state;
  - creates an `auth_sessions` row;
  - sets `__Host-` cookie flags (HttpOnly, Secure, SameSite=Strict, Path=/);
  - writes the audit event `session.started`;
  - redirects to `/signin/callback?to=<safe path>`.
- **AC 5.1.3 (SHL-06g).** *Given* `/signin/callback`, *then* the AuthCard shows a 14 px spinner and "Signing in…" (`aria-live`). It calls `POST /v1/auth/refresh` to get an in-memory access token, loads `/v1/me`, and navigates to the safe return path, or to `/home` (`/engagements` in production until HOME-01 is live).
- **AC 5.1.4 (refresh and timeouts).** *Given* an access token near expiry, *then* the client calls `/v1/auth/refresh` (cookie plus the CSRF header). The BFF rotates the cookie value, returns a new access token, and enforces the idle and absolute timeouts set in ADR P-54. *Given* a reused (rotated-out) cookie value, *then* the session is revoked and `session.refresh_reused` is audited. *Given* expiry anywhere, *then* the user returns to sign-in and back to the same route (`safeReturnTo`, existing).
- **AC 5.1.5 (step-up).** *Given* an action needing fresh MFA (the existing `ConfirmItsYou`), *then* the client restarts sign-in with forced re-authentication [verify AuthKit parameter] and the session's `mfa_at` updates. The access token never sits in `sessionStorage` or `localStorage`.
- **AC 5.1.6 (CSP).** *Given* the BFF code exchange, *then* the firm build's `connect-src` is back to `'self'`. The IdP authority entry in chapter 04 §1.4 is removed, because the SPA only navigates to AuthKit and never fetches from it.

### 3.6 Invariants across the epic

- **INV-1, the agent never decides.** No notification kind with an agent-originated actor carries an inline action (AC 3.1.9).
