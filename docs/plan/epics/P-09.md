# P-09 · Agent transparency v1: run dock & trace

> Epic specification and task backlog. Chapter 01 is the plan of record for dates, owners and scope. Decision and ADR IDs are chapter 09's (DEC-nn, ADR P-nn; repo ADR numbers are the reservations in F-02's schedule). **AY** = ayushkbhatia, **N** = notanaskhan. The CSV twin of §9 is `sections/epics/P-09.tasks.csv`.
>
> **Short version.** P-09 makes the Accrued Agent's work visible, and nothing more. It ships two P0 screens over the agent runs that already exist and over the runtime-v2 tables that P-10 migrates by Dec 24, 2027:
> 1. **SHL-13, the agent dock** (the 330 px "Agent" pane of the T2 record cockpit). It shows the run projection by level, narration, tool cards in six states, questions, inline decisions, failures and the completed run.
> 2. **WB-09, the run trace drawer** (O2, 480 px, over any page through `?ov=run-trace:<runId>`). It shows every tool call, the records read with counts and sources, proposed writes and who decides them, the model label, the region and the training statement. Traces export as deterministic JSON and PDF with a signed manifest.
>
> P-09 also defines **`AgentBlocks`** (ADR P-24 / AG-05): the closed, structured output schema that every later agent surface renders. It also builds the **E6 run store** (`RunStore`, `ScriptedRunSource`, `PollingRunSource`) that F-07, W-02, I-02, C-01, T-05 and K-03 reuse.
>
> **Read-only means:** P-09 adds no write endpoint, no table, no Temporal workflow and no model call. Data reaches the screens by **polling until P-10's SSE lands**. The dock's human buttons ("yes, run it", answer, Retry, Sign off run) are **intents**. Each one calls a C6 v2 route that P-10 owns, and it renders only when the server lists that action in `allowed_actions`. The whole epic merges **dark** inside the Jan 1 – Apr 20, 2028 freeze window (chapter 01 §1.2.4).

### 3.7 AgentBlocks: structured agent output (ADR P-24)

**Story 7.1. A closed set, rendered as nodes, numbers by reference.** As every agent surface, we render agent output safely and identically.
- *Given* any agent-authored item, *then* its payload validates against `AgentBlocks v1`, a closed discriminated union of parts:
  - `p` (segments `[{kind:"text", text} | {kind:"cite", citation_id, n} | {kind:"fact", fact_id}]`);
  - `table` (head plus rows of text/fact/cite cells);
  - `kv`;
  - `metric` (label plus fact);
  - `file` (artifact id, name, meta);
  - `badge`;
  - `cite_list`;
  - `options` (key, title, detail, recommended);
  - `entity_ref` (record type plus id; the label is rendered by code).
  
  Any other part, any HTML or markdown, and any URL not on the output link allowlist is rejected.
- *Given* a `text` segment containing a numeric token that is not a `{fact}` reference or a verified citation value, *then* the number-provenance check rejects it (ADR P-48). Inside `converse()` the turn is repaired once, and after that the value is marked "Unsupported" (DE-3).
- *Given* text that claims a human act ("approved", "signed off", "I decided", "sent"), uses banned words ("memory", "trained", "learned"), uses "!", puts a confidence percentage on a verdict, names a persona, or uses a status word outside the registry, *then* the deterministic copy lint rejects it (DE-5; I-12).
- *Given* the browser, *then* `AgentBlocks` renders React nodes only. Every string passes `sanitiseAgentText`, every `{fact}` renders through `format.ts`, every cite renders a `CiteMarker` (C4), and an unknown part kind renders a neutral row with no raw payload. ESLint L4 fails any component that prints an agent field outside `AgentText`, `AgentProse` or `AgentBlocks`.

## 6. Accrued Agent

- **Capabilities, tools, prompts:** **none new.** P-09 makes no model call and changes no prompt or capability spec, so freeze rule 4 (no model or prompt upgrade without the full suite and a shadow run) is not triggered.
- **What P-09 adds around the agent:**

  **Threshold: 1.0 on every case on every repeat.** It runs on PRs touching `blocks.py` or `output_checks.py` and nightly. Reports are HMAC-signed like the existing suites. The existing suites (`evals/screening`, `upload_review`, `matching`, `guidance_drafting`) must stay green and unchanged.
- **Data boundary:** traces and the projection are deterministic, so they are not boundary-gated (chapter 05 §5.7.3, G-0 only). Model-backed items appear only where the producing capability is cleared. DF4a/DF4b say so.
