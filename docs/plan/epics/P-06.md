## 1. Goal and user-visible outcome

**Goal.** Turn the repo's one-list-per-engagement PBC board into the requests and binders engine that every service line uses: binders as many `request_lists` per work item with a real lifecycle (Draft → Published ↔ Unpublished → Complete → Closed), requests with the migrated status set (Draft · Requested · Uploaded – needs review · Received ✓ · Returned · Not applicable, Overdue derived) plus the client's own words (To do · Done · Ignored), a request composer with a live recipient preview, an evidence-screening aggregate a person can act on, follow-ups the platform drafts from the firm's templates and a person sends, and the one enumerated exception to "nothing is ever deleted": a client may withdraw an upload the firm has not accepted. Freeze **C5 v1** so A-01, R-01, T-02 and C-01 build on one schema. The agent proposes and drafts; a named person publishes, sends, accepts and returns (INV-1).

## 3. Features & user stories

Invariants referenced: **INV-1** the agent never decides; **INV-2** citations shown are verified; **INV-3** walls hold (404, not listed); **INV-4** portal scopes are isolated; **INV-5** attribution is correct ("‹person› via Agent", never "Accrued Agent" as approver or sender).

### 3.1 Binders: create, publish, unpublish, duplicate, complete, close

**Story 1.1.** As Kevin Osei, I start the TY2026 Feld binder from last year's and publish it when it is right.
- *Given* the Feld TY2025 binder with 7 requests, *when* Kevin creates a binder on the TY2026 Form 1040 work item from it, *then* a Draft binder appears with 7 requests in status `draft`, each tagged "From 2024 return" where the prior request carried that tag, categories preserved, guidance copied and still-needed notes dropped (`roll_forward.py` rules), and every row reads "Not published" (BND-02b).
- *Given* a Draft binder whose engagement has not met G3, *when* anyone publishes, *then* the API answers 409 `binder_gate_unmet` with the gate facts, and the button shows the read-only reason from `allowed_actions`; an `intake` binder publishes before G3 (DEC-39).
- *Given* G3 is met and two requests lack a due date and the binder has no default, *when* Kevin publishes, *then* 422 `due_date_required` lists both item IDs and nothing changes (SHL-14e logic at binder level).
- *Given* a valid Draft, *when* Kevin publishes with an `Idempotency-Key`, *then* the binder becomes `published` (`published_at/by`), every draft request with client visibility becomes `requested` with `requested_at`, internal-only requests stay internal, one `binder.published` email per recipient is dispatched after the 10-s Undo window (DEC-24), the audit log records `binder.published` with Kevin as actor, and a retried POST with the same key returns the same response without a second email.
- *Given* the publish toast, *when* Kevin clicks Undo within 10 s, *then* `binder.publish_undone` is written, the binder and its requests return to `draft`, and no email leaves.

**Story 1.2.** As Remy Vidal, I pull a binder back while I fix two requests.
- *Given* a published binder, *when* Remy unpublishes without a reason, *then* 422 `reason_required`; *with* "fixing 2 requests", *then* status `unpublished`, `unpublished_at/by/reason` recorded, client principals get 404 for the binder and its requests at once (INV-4), and BND-01 shows "Unpublished Sep 2 by Remy Vidal — fixing 2 requests" (BND-01c).
- *Given* the binder is republished, *then* only requests sent since the unpublish generate client email *(inferred: no duplicate "your binder" email)*.

**Story 1.3.** As Grace Holloway, I run a second-part binder on the same return.

**Story 1.5.** The binder closes when its work is finished.

### 3.9 Cross-cutting invariants

**Erase mechanism (ADR-137 decision; recommended).** The repo's storage is content-addressed (`tenants/<tenant>/sha256/<fingerprint>`), deduplicated, sealed with a per-object data key wrapped *inside* the object (`kernel/crypto/__init__.py` envelope "ABE1"), and kept in Object Lock GOVERNANCE with retention extended on reuse (`evidence/storage.py`). Deleting early would need the break-glass `abacus-retention-override` role (chapter 06 C-09), which is wrong for a routine 30-day job. So client-channel uploads are written in **detached-key mode**: key `tenants/<tenant>/v/<version_id>` (never shared by deduplication), envelope "ABE2" whose wrapped data key lives in `evidence_object_keys`, not in the object. Acceptance stamps `retained_at` (the key is then permanent). Erasing destroys the wrapped key: the ciphertext is unreadable at once and ages out under its retention. Firm uploads, retrievals and generated files stay content-addressed. Duplicate detection keeps using the fingerprint column (DEC-58 g). Alternative (b), a short rolling retention extended on acceptance and deletion on lapse, erases later than 30 days and is not recommended.
