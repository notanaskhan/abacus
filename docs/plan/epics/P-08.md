## 1. Goal and user-visible outcome

**Goal (chapter 01 §1.4.3).** Ship the white-labelled portal shell and client identity: WorkOS email-code sign-in with lockout, a role-union home, `client_access_grant` enforcement with `scope_only`, MFA mandatory for owners, signers and approvers, and a host-resolved branding route. The portal is "Brightwater Hale's portal": the firm's mark, name, address and people, and nowhere the word Accrued. Sign-in never reveals whether an email has an account. Every number on the home page ties to a firm-side count, and every aggregate is filtered by the grant that covers its own target scope, so role union never leaks one scope into another (INV-4).

## 3. Features & user stories

Invariants are cited as **INV-1** (the agent never decides), **INV-2** (citations verified: no citation reaches the portal, so this holds trivially), **INV-3** (walls hold: walls bind staff, so they matter here only for firm-side unlock and reset), **INV-4** (portal scopes isolated) and **INV-5** (attribution correct). State references such as POR-01f are the artboards in §2.1.

### 3.1 The firm's portal on the firm's host

**Story 1.1.** As Claire Feld, I see Brightwater Hale, not a software vendor, when I open my portal.
- *Given* the E0 load with the branding row for Brightwater Hale and the host `brightwaterhale.<neutral-portal-domain>` active, *when* the SPA's root loader calls `GET /v1/portal/branding`, *then* the response carries only Public fields (`firm_name`, `portal_name`, `logo_url`, `address_line`, `help_url`, `privacy_url`, `support_contact_name`, `secured_footer: false`, `sign_in: {methods: ["email_code"], mfa_floor: ["owner","signer","approver"]}`, `maintenance_banner: null`), and POR-01a renders the mark, name and footer with no "Accrued" anywhere (L7 crawler).
- *Given* a host that is not in `portal_domains`, *when* branding is requested, *then* the response has the same shape with neutral values and the SPA shows a neutral card with no firm data. No tenant identifier is returned on any host.
- *Given* the logo, *when* `GET /v1/portal/branding/logo` is called, *then* a server-re-encoded PNG is served same-origin (CSP `img-src 'self'`) with an ETag.

**Story 1.2 (host pinning, INV-4).** The host is a branding hint only.
- *Given* a portal session minted on Brightwater Hale's host, *when* the same access token or refresh cookie is presented on another firm's portal host or on the firm app host, *then* the API answers exactly as for no session (401 `unauthenticated`), and `test_portal_host_pinning.py` proves the `Host` header changed branding only, never the authorisation tenant.
- *Given* a staff session from the firm app, *when* it is presented on a portal host, *then* it is refused the same way.

### 3.2 Passwordless sign-in without enumeration

**Story 2.1.** As Claire Feld, I sign in with an emailed code and no password.
- *Given* Claire is a contact with an active grant, *when* she submits her email on POR-01a, *then* `POST /v1/portal/auth/start` returns **202** `{challenge_id, code_expires_at, resend_available_at}` after a padded minimum duration; the outbox event `portal.sign_in_code_requested` (identifiers only) leads `communications` to obtain a fresh code from `identity` in memory and send it in the firm's name through the C16 template `portal.sign_in_code`; the stored message has the code redacted; POR-01b shows Resend disabled until `resend_available_at` (the artboard shows 0:42).
- *Given* any of: an unknown email, a staff member of the firm, a contact with no active grant, a contact in another firm, or a locked email, *when* the same request is made, *then* status, body shape and timing (within the tolerance the AC suite fixes) are identical, no email is sent, and no tenant audit event names a person who does not exist (only a security metric with a hashed fingerprint is kept).
- *Given* Claire pastes `481027` in fixture mode (a real random code on staging), *when* the sixth digit lands, *then* the form submits once and she lands on POR-02 (`/v1/me.portal.shell = "full"`).

**Story 2.2 (wrong code and lock).**
- *Given* a wrong code, *then* `401 code_mismatch {tries_left: 2}`; POR-01f shows the inset red-ink ring and the helper in a polite live region; the audit event `portal.sign_in.failed` names the contact when one exists.
- *Given* the third wrong code for the same email within the window, *then* `423 sign_in_locked {locked_until}` 15 minutes ahead on `kernel.clock`; POR-01g names the branding support contact (Grace Holloway); `portal.sign_in.locked` is audited; the contact's `portal_state` becomes `locked` through `organisations.api` and returns to `active` at `locked_until` or on a firm unlock (§3.7).
- *Given* a resend, *then* the old code stops working and the tries **do not reset**. *Given* a code older than 10 minutes, *then* `410 code_expired` and the copy-keyed helper offers Resend.
- *Given* a locked email that does not exist, *then* the same lock and the same screens apply, so the lock is not an existence oracle.

**Story 2.3 (role-routed landing, INV-4).**
- *Given* successful verification, *then* the landing comes from `portal_scopes`: full shell → `/` (POR-02); third party only → `/requests` (POR-14); K-1 only → `/k1s` (POR-13); TCWG only → `/governance` (POR-15); prospect → `/intake` (POR-18); component auditor → `/component-room`. In fixture builds an unbuilt landing renders "Not built yet".

### 3.3 Two-step verification for owners, signers and approvers

**Story 3.1.** As Tess Moreno, owner of Copperleaf, I confirm my identity with an authenticator, as Brightwater Hale requires.
- *Given* Tess holds an `owner` grant, *when* her code verifies, *then* the response is `{state: "mfa_required", mfa_token}` (5-minute, single use) and POR-01c renders; a correct TOTP through the WorkOS factor yields a session with `mfa_at` set; `portal.mfa.verified` is audited.
- *Given* "Trust this device for 30 days" is on, *then* a `__Host-` trusted-device cookie bound to Tess and this tenant is set, `portal.device.trusted` is audited, and sign-ins within 30 days (the firm may set fewer, never more) skip POR-01c.
- *Given* three wrong TOTP codes, *then* the same 15-minute lock as codes applies (`423 mfa_locked`).
- *Given* "Use a backup code", *then* one of Tess's 8 hashed codes verifies once and is marked used; reuse is refused.

**Story 3.2 (the floor is code; INV-1, INV-4).**
- *Given* the floor predicates registered with `identity.register_mfa_requirement` — any active `owner` grant (identity) and any `engagement_contacts` designation `approver_of_record`, `signing_officer` or `ske_designee` (engagements, DEC-63) — *when* any predicate is true, *then* MFA is required. *Given* a predicate raises or times out, *then* MFA is required (fail closed).
- *Given* Claire Feld (taxpayer, no designation) and the firm extension off, *then* Claire is not asked for a second step (POR-01a → b → POR-02a as designed). **When T-01 registers the TRI predicate (DEC-34: "MFA is required for TRI-bearing scopes"), Claire's 1040 scope will require it** (§11 R6).
- *Given* `portal_security_policies.mfa_for_all_client_users = true`, *then* every client user of the firm is asked; no setting can exclude a floor role (stricter-only, the P-10 ceiling rule).

**Story 3.3 (first-time setup, DF-17).**
- *Given* a user who must use MFA and has no factor, *then* verification returns `{state: "mfa_setup_required", mfa_token}` and the c′ setup state shows a QR code and manual key; verifying a first code enrols the factor, shows 8 backup codes once with a confirm step, and audits `portal.mfa.enrolled`. Declining leaves the user without a session; there is no bypass.

**Story 3.4 (revocation).**
- *Given* `access.changed` or `client_access.revoked` for a user, *then* that user's portal sessions in the tenant end and trusted devices are revoked within one relay cycle (p95 ≤ 5 s), audited as `session.ended` (reason `revoked`) and `portal.device.revoked`.

### 3.4 Accepting an invitation

**Story 4.1.** As Sam Ortiz at Keystone, I see exactly what Brightwater Hale is asking of me before I accept.
- *Given* the invitation link (token in the URL **fragment**, moved to tab storage and removed from the address bar as `ClientAccept.tsx` does today), *when* `POST /v1/invitations/preview {token}` runs, *then* POR-01d shows firm "Brightwater Hale LLP", organisation "Keystone Retirement Services", "Requests delegated to you" and **9 items** for the Northwind Robotics 401(k) Plan; the email row is read-only.
- *Given* the terms toggle is off, *then* "Accept and continue" is disabled. *Given* it is on, *when* Sam continues, *then* `auth/start` runs with the invitation token, POR-01b follows, and after verification `POST /v1/invitations/accept {token, terms_version}` creates the 9 request-scoped `third_party` grants through `identity.api.grant_client_access` in one unit of work, records `terms_accepted_at`, marks the invitation accepted and the contact active, and audits `client_invitation.accepted` and `client_access.granted` **attributed to the person who invited Sam** (INV-5).
- *Given* a token that is expired (more than 14 days), used, revoked, malformed, or for a staff member of the firm, *then* preview and accept answer the same `404`.
- *Given* Sam's session, *when* it calls `GET /v1/portal/home`, *then* `404` (no full-client role; INV-4), and the SPA lands on `/requests`.

### 3.5 Renewing an expired link

**Story 5.1.** As Claire Feld, I can get a fresh link when an old reminder has expired.
- *Given* a reminder link issued by `communications.api.issue_secure_link` more than 14 days ago, *when* Claire opens it, *then* POR-01e renders; "Email me a new link" calls `POST /v1/portal/links/renew {link_token}`, which answers **202** for any token, sends a new link **only to the address the original was sent to**, and shows the toast "New link sent to claire.feld@gmail.com"; `portal.link.renewed` is audited.
- *Given* a malformed or unknown token, *then* the SPA shows POR-01a (tokens are 256-bit and unguessable, so validity reveals no account).
- *Given* an expired, never-accepted invitation, *then* renew re-issues it to the same address at most twice and the firm sees "Renewed by recipient" on the invitation (P-07 shows it); revoked invitations are never renewed.

### 3.6 Home

**Story 6.1.** As Claire Feld, one page tells me what Brightwater Hale needs now, where my return stands and who my team is (POR-02a).
- *Given* E0 and Claire's taxpayer grant on the Feld household scope, *when* `GET /v1/portal/home?scope_id=…` runs, *then* the to-dos are composed by `home_sources`: the upload count equals the binder's open client-visible requests from `requests` (`your-part`), which ties to TAX-03 "Intake 2" when T-02 ships; the binder card reads 19 of 21 with 37 sorted; the work card's stage comes from `stages.py` over the C2 code and reads ◐ Review with the pill "We're reviewing your return"; the team carries role codes the frontend renders as "Partner — signs your return", "Manager — reviews your return", "Preparer — your day-to-day contact" and "Client service".
- *Then* no field carries a firm status code, an amount, materiality, an agent name or confidence (contract test T02, DTO test T22).

**Story 6.2 (first visit, POR-02b).** *Given* Claire has never signed in before and has not dismissed the welcome for this scope, at the Feb 2, 2026 clock, *then* the welcome card renders; dismissing it calls `PUT /v1/portal/preferences {scope_id, welcome_dismissed: true, version}`, which persists per user and scope and audits `portal_preferences.updated`.

**Story 6.3 (all done, POR-02c).** *Given* no open to-dos of live kinds, *then* the green-tint card "You're all set for now." renders with the next-step line for the work-item kind.

**Story 6.4 (overdue entity owner, POR-02d).** *Given* Tess's owner grant on Copperleaf (an entity scope), *then* the nav includes Approvals, and red tint appears **only** on the to-do whose earliest open request is past due (P-06's derived overdue), as "Overdue · due Sep 5"; nothing else is red.

**Story 6.5 (role union, POR-02e; INV-4).** *Given* Meera Shah's `taxpayer` grant on her own 1040 and `k1_recipient` grant on a Ridgeline K-1 package, *then* `/v1/me.portal.scopes` lists both with role labels, the shell is full, the home for her 1040 scope shows her own work card and (fixture until T-02) the My K-1s card, and any request for the Ridgeline return's work item, binder or team answers 404. `test_portal_scope_isolation.py` proves it for every home source.

### 3.7 Firm-side recovery and control

**Story 7.1 (unlock).** *Given* a locked contact, *when* Grace Holloway (`client_service`) or a firm or security admin calls `POST /v1/clients/{client_id}/contacts/{contact_id}/portal-unlock`, *then* the lock clears, `portal.sign_in.unlocked` names Grace (INV-5), the agent and system principals are denied at the matrix and live-human layers (INV-1), and a staff member walled from the client gets 404 (INV-3).

Audited as `portal.mfa.reset`; agent denied (OQ-1 confirms the policy).

**Story 7.3 (pause).** *Given* a founder sets the per-firm `portal_sign_in_paused` control, *then* `start` and `verify` for that firm's hosts answer `503 sign_in_paused` within 10 seconds, existing sessions are unaffected, and the SPA shows the paused state.

### 3.8 Sessions

**Story 8.1.** *Given* a portal session, *then* it lives in `auth_sessions` with `surface = 'portal'`, `pinned_tenant_id` and `portal_host`; the refresh cookie is `__Host-`, HttpOnly, Secure, SameSite=Strict; refresh requires `X-Abacus-CSRF` and an Origin check; a reused refresh value revokes the session (`session.refresh_reused`); idle and absolute timeouts follow ADR P-54; "Sign out" in the user menu ends the session and returns to POR-01a.

**Budgets (inferred, fixed in the SPEC).** `start` and `verify` p95 ≤ 400 ms server time excluding email; code email send-start p95 ≤ 5 s after `start` (outbox relay); `GET /portal/home` p95 ≤ 300 ms for one scope with ≤ 50 work items; branding cached at the edge 60 s keyed by host.
