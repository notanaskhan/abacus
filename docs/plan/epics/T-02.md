## 3. Features & user stories

Invariants referenced: **INV-1** the agent never decides; **INV-2** citations shown are verified; **INV-3** walls hold (404, not listed, not counted); **INV-4** portal scopes are isolated (role union, K-1 recipients, inquiry addressees); **INV-5** attribution is correct ("‹person›", "‹person› via Agent", never "Accrued Agent" as approver, releaser or sender).

### 3.1 Return record and status machine

- *As Samuel*, I want every return to carry one canonical status the server guards, so that no screen or drag can approve, send or file.
- **Given** the Feld return in `in_review` · manager, **when** any client posts `PATCH`/`POST …/transitions` to `approved`, `ready`, `awaiting_signature` or `filed`, **then** the API answers 409 `{gate: "final_approval" | "export" | "envelope" | "transmission"}` and nothing changes; only T-01's `tax/approval.py` (T-01-T18), `export.py` and `filing.py` may apply those transitions (static rule TAXAPPROVE-001, registered in T-01-T07).
- **Given** a binder on a `not_started` return is published (P-06 `request_list.published`), **then** the return moves to `gathering` by the system with an audit event "Return moved to Gathering · binder published by Kevin Osei" (INV-5).

- **Given** C3 sign-offs on the return reviewable, **then** the preparer's L1 moves it to `prepared`, the detail reviewer's "Start review" moves it to `in_review`·detail (inferred event), the detail reviewer's L2 to `in_review`·manager, and the manager's L3 to `in_review`·partner; `action_required` is derived from open issues with `blocks ∋ final_approval` and is never stored; "Prepared" renders neutral on TAX-01 tiles and as a state pill elsewhere (C2 context labels).
