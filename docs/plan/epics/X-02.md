### 4.5 Temporal workflows and activities

- **`GrcSyncWorkflow`** (`integrations/grc/workflow.py`). One per sync (`grc-sync:<grc_sync_id>`), work class `background`.
  - **Schedule.** Driven by a Temporal Schedule created through `kernel.dispatch.schedule()` (P-50) every `interval_minutes`, which signals `tick`.
  - **Signals.** `sync_now` (60-second debounce), `pause`, `resume`, `outbound_enqueued`, `reauthorised`. A tick during a run is coalesced; `continue_as_new` after 96 runs (one day).
  - **Activities**, in order. Each authorises its own system action and is idempotent:
    1. `grc.pull` — `connections.api.pull(dataset="grc_requests")` with `changes_since` and the cursor. It writes a `sync_runs` row (trigger `schedule`), which appears in the client-visible access log.
    2. `grc.diff` — pure code over the stored raw bytes and the links. It records `grc_sync_remote_events` (idempotent unique key), conflicts, the inbound file list and wording changes (ignored).
    3. `grc.receive_files` — for each new attachment, `fetch_attachment`, then the evidence upload processing workflow as a child (scan → isolate → screen), giving an evidence version with method `grc_sync` on the linked item in "Uploaded – needs review".
    4. `grc.drain_outbound` — runs only if the sync is `active`, the kill switch is off and the connection is `active`. For each queued `write_operations` row in order: `integrations.execute_write` → `writers/drata.py`, with preflight (still client-visible and all-users, link `linked`, approval actor still holds the action, payload hash equals the current portal-visible projection), idempotency key, read-back and write-once `write_evidence`.
    5. `grc.record_run` — finishes the run with counts, emits outbox events and updates the C13 gate.
  - **Reauth.** A 401 or 403 from the provider ends the run as `needs_reauth`, marks the connection `needs_attention` (reason `needs_reauth`, A-02), moves the sync to `needs_reauth` and queues outbound work. `reauthorised` (from `connection.reauthorised`) resumes.
  - **Errors.** Errors cross to Temporal as class names only (connections README rule). Payloads are sealed by `kernel.crypto.payload_codec`. `workflow.patched(...)` is used for any change. A replay history goes in `backend/tests/workflows/histories/grc-sync-v1-*.json` *(new)*, plus `test_grc_sync_replay.py` beside the existing replay tests.
- **Outbound subscriber** (`integrations/grc/subscriptions.py`, outbox consumer, idempotent on `event_id`). On a `request_item.sent`, `.due_changed`, `.visibility_changed` or `.status_changed` event for an engagement with a sync, it acts only if the event's actor is **human** and the item is client-visible to all users:
  - it queues a W5 operation with `approval_event_id`, or, for a visibility change to Owners only, moves the link to `unlinked_owners_only`;
  - agent-attributed events never queue anything (DB CHECK, §4.2).
- **No new workflow for readiness.** Completion is an outbox subscriber on `sign_off.created`/`sign_off.removed` for the readiness sheet. Exports are C11/K-03 render jobs.

#### 4.10.3 W5 amendment decisions (T01, inside the chapter 09 amendment of DEC-69 and P-16)

1. W5 is **request metadata only**: title and description as the client already sees them, due date, and status. It never sends files, firm comments, control states or test results.
2. **Never delete**, in either system. A remote deletion is data.
3. **Event-derived approval** (replaces P-16's "approved batches" for W5 only, per the chapter 09 amendment). Every write traces to a human-attributed event, and the approver's live rights and the payload hash are re-checked at execution. This is the documented alternative to one P-35 `approval_grant` per queued write: a queue that drains after a pause would otherwise hold stale grants.
4. **Attest clients allowed for W5 only** (per the chapter 09 amendment of DEC-69 option (b); I-POLICY-NOT-ATTEST is unchanged for W1). The rationale: no client records are touched, the firm's own requests are written into the client-designated audit workspace, and there is no management function.
5. Owners-only and draft exclusion.
6. Queue semantics.
7. Auth mode: OAuth if Drata's partner programme offers it, else a client-generated API key entered once by the client admin in POR-16 under the chapter 06 §7.1 exception, sealed at once and never displayed.
8. Delta pen test before the first real-firm write.
