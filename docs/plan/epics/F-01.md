## 1. Goal and user-visible outcome

**Goal.** Make two founders working in parallel through Claude Code safe from day 1. Concretely:
- nothing new lands unreviewed;
- `main` is green and stays green;
- neither founder can approve their own change;
- two worktrees on one laptop never share a database;
- a local build never competes with a hosted build for the same database;
- merges ride a batched release train instead of deploying per fix.

Today none of this holds (ch. 02 §2.3.1):
- the repo is public with no ruleset (D1, D2);
- PR CI has not been green since Oct 7, and `main` runs stage 1 only (D3, D4);
- the nightly e2e has been red since Oct 8 (D5);
- the hook accepts only `approved_by: founder` and freezes any migration that exists on disk (D9);
- the ports and the compose project name are fixed (D17).

**What a named Brightwater Hale person can do when this ships.** No firm user sees F-01. Brightwater Hale is the synthetic tenant, and nothing in F-01 renders a screen. The indirect outcome is still concrete. When **Felix Andersen** (Brightwater Hale's IT/Security persona, ch. 04 §6.5) sends a vendor-security questionnaire, Accrued can answer the change-management questions (SOC 2 CC8.1) with evidence instead of intent:
- the repository is private;
- every change to `main` was approved by a named founder who did not author it;
- required checks ran on every merge;
- secrets are scanned on push;
- production releases are approved through a reviewed PR (the release side is Q-01).

**Margaret Okonkwo** (Managing Partner persona) can be told that no AI coding agent approved or merged its own work: a repo-level analogue of INV-1 (the agent never decides) and INV-5 (attribution correct).

**What the founders can do when this ships (the real users).**
- **AY** opens a worktree for a screen task and runs `make dev-fixtures` with Docker stopped. AY never collides with N's `make dev` on the same machine, and AY's PR finishes required checks in ≤ 6 minutes without running backend shards.
- **N** renumbers an unmerged `0057_*.py` migration after a rebase without asking for an approval file. N cannot approve their own protected-path change, and a migration or staging operation is refused while a hosted deploy is in flight.
- **Both** merge approved PRs together in the Tue/Thu window through `make batch`. Each Friday they see escaped defects and review-queue ages against the SLAs.

## 3. Features and user stories

F-01 has no screen states. Acceptance criteria reference repo artefacts and two repo-level analogues of the product invariants:
- **INV-1(repo):** no AI coding agent approves, merges or self-authorises a change; only a named human founder can.
- **INV-5(repo):** every change on `main` is attributable to an author and a different named approver.

INV-2 (citations), INV-3 (walls) and INV-4 (portal scopes) are not exercised. F-01 must not weaken the tests that assert them.

### F1 · Repository safety (T01)

*As N, I want the full history scanned while the repo is still public, then the repo made private inside an org both founders own, so that anything exposed is rotated and nothing new leaks.*

- **Given** the repo is public at `a42034c` with 144 remote branches, **when** GitHub secret scanning alerts are reviewed and `python -m abacus_tools.quality.secrets_scan --history` runs the existing rules over every blob in every ref, **then**:

- **Given** that record, **when** the repo moves to a GitHub organisation on the Team plan and is set private, **then**:
  - the repository API reports `visibility: private`;
  - both founders are org owners and member 2FA is required;
  - `github.com/notanaskhan/abacus` redirects;
  - the exposure window (Oct 4 → transfer date) and the fork count are logged as a SOC 2 risk-assessment entry.
- **Given** the private repo, **then**:
  - Secret Protection push protection and Dependabot alerts are on;
  - Actions are limited to SHA-pinned actions;
  - the default `GITHUB_TOKEN` is read-only;
  - `delete_branch_on_merge` is true;
  - merged remote branches are deleted;

### F2 · Review by the other founder, enforced server-side (T01, T04, T06)

*As either founder, I want GitHub itself to require the other founder's review, so that review cannot be skipped by a tired human or an eager agent (INV-1(repo), INV-5(repo)).*

- **Given** an approved PR, **when** a new commit is pushed, **then** the approval is dismissed, and merging needs an approval of the most recent push.
- **Given** any credential, including a Claude Code session using a founder's token, **when** it pushes directly to `main`, force-pushes or deletes `main`, **then** the ruleset rejects it. The bypass list is empty, and linear history (squash or rebase) is enforced.

### F3 · Protected-path hook for two founders (T04; tests T03)

*As N, I want to renumber my own unmerged migration after a rebase without an approval file. As AY, I want to approve N's protected-path work but never my own.*

### F6 · PR hygiene and the review record (T12)

*As the reviewing founder, I want every PR to declare its migration, size, zone, reviewers and test author, so that ADR-078, ADR-083 and ADR-084 hold with two founders.*

- **Given** a PR that adds a file under `backend/migrations/versions/`, **then**:
  - exactly one migration file is added;
  - the PR title contains `[mig NNNN]`, and NNNN equals the file's number;
  - the file's `revision` and `down_revision` chain onto the base branch head.
- **Given** a PR's hand-written lines (excluding `linguist-generated` paths, lockfiles, `**/fixtures/**`, snapshots and `durations.json`), **then** it gets a label `size/S` (≤300), `size/M` (≤600), `size/L` (≤1,200) or `size/XL`. Above 600 lines a comment cites the ~600-line target (chapter 01 §1.3.3). Above 1,200 lines the check fails unless the body carries a `Size exception:` line.
- **Given** a PR that adds an ADR, SPEC or TASK ID from the other founder's block, **then** the check fails unless the body carries a `Number override:` line naming the reservation issue.
- **Given** a PR's zone, **then** the zone is red if any path matches `_protected.PROTECTED`, otherwise the higher of the zone in the PR checkbox and the path map. The path map is a constant in `review_record.py`, aligned with the ADR-086 `zones:` example (`apps/web/src/components/**` and `docs/**` are green).
- **Given** an amber or red PR, **then** the check fails unless the PR body's Reviews table has:
  1. every reviewer-agent row filled (architecture, security, test, plus AI when agent paths changed);
  2. `Reviewer model:` different from `Author model:` (ADR-084; the exact rule is set in ADR-116, see §11 Q2);

- **Given** the check fails, **then** its message names the missing row. It never edits the PR.

### F7 · Release train: batched merges (T13, T14)

*As both founders, we merge approved work together in fixed windows, so each batch costs one build and one staging deploy, never one per fix (working agreement; DEC-54 / P-56).*

- **Given** an approved, green PR labelled `hold-for-batch`, **when** it is outside a window, **then** the required `merge-window` status is pending, and the PR shows "holding for the batch (next window: Thu Nov 5, 17:00 CT)".
- **Given** the window opens on Tue or Thu at 17:00 America/Chicago, **then** `merge-window.yml` sets `merge-window` to success on every approved, green `hold-for-batch` PR. Cron runs at 22:00 and 23:00 UTC, and the script checks local time, so the Nov 1, 2026 DST change is handled. At 19:00 CT the status returns to pending on unmerged PRs.
- **Given** a window, **when** a founder runs `make batch`, **then** the tool:
  - lists the eligible PRs;
  - squash-merges them in order (contract stubs first, then by declared `Depends on:`, then by approval time);
  - stops at the first conflict or red required check;
  - prints a batch manifest (PR numbers, merge SHAs) and posts it to the pinned "release train" issue.
  
  Q-01's staging deploy runs once per batch.
- **Given** a PR labelled `ship-now`, **then** `merge-window` is success immediately only if the body has `Ship-now reason: production-broken | security-fix | explicit-request by @<handle>`. The reason is copied to the release-train issue.
- **Given** a push to a PR, **then** no preview is built. The `preview` label is the only trigger, and Q-01 implements the build.
- **Given** ADR P-56 (amends ADR-088: "main deploys to staging once per batch"; production weekly through the release PR; hotfix lane; opt-in previews; never a local production build against a hosted database), **then** both founders accept it by **Fri Nov 13**, and `docs/process/release-train.md` describes the operating procedure.
